Why a schema proposal is necessary
The existing growth ledger has no honest kind for full-source awards of
0/1/5/10. Reusing practice/admin/attendance kinds would break its meaning and
constraints. The additive SQL lives outside migrations and is not loaded by
scripts/migrate.ts. Absent its table, the new endpoints fail closed with 503
source_attempt_schema_not_ready. Actual credit is not enabled by this branch.
Do not promote this SQL into migration tooling or execute it without separate
schema approval and the remaining acceptance checks below.

Client interface (independent from all practice/workspace saves)
POST /api/v1/textbook/semantic/full-attempts/:id
GET  /api/v1/textbook/semantic/full-attempts/:id?gradingVersion=2
For a pinned source revision, prefix the same paths with
/api/v1/textbook/revisions/:sourceRevision/semantic/full-attempts/:id
(in place of /api/v1/textbook/semantic/full-attempts/:id).
History81 joseon/goryeo/opening use the existing authoritative script loader.
Both JWT/live-session authentication and TextbookMemberGuard are required.
The authenticated user supplies ownership; responses are private/no-store.

POST body:
{
  "attemptId": "one UUIDv4 generated once for this full attempt",
  "mode": "full",
  "status": "completed",
  "version": "exact 64-character source version from the existing workspace",
  "gradingVersion": 2,
  "responses": [{"itemId": "every authoritative item once", "values": ["every required slot"]}]
}
Unknown fields, selected review subsets, practice/paused/active modes, empty
slots, duplicate or unknown items, incomplete rosters and stale new submissions
are rejected before completion storage. Server grading is unchanged and uses
the explicit existing grading version; no client grades/XP/timestamps accepted.
The API completion submission is the full-attempt boundary: it cannot prove
the browser's earlier mode or unaided answering. The frontend must call it only
after a completed full quiz, never on a practice save, interruption or pause.
Do not create a fresh attemptId on retry. The existing quiz exposes answers;
this feature is not an anti-cheating system or an attempt-start provenance log.

POST returns {attempt,replayed}; attempt contains id, sequence (string), scope,
correct, total, xpAward and completedAt. One item is correct only if all its
required answer slots pass the unchanged grader. XP uses integer comparisons:
correct*100 >= total*80:10; >=total*70:5; >=total*60:1; otherwise:0.
No rounded display percentage affects the award. Existing partner attribution
and XP application triggers process exactly one dedicated ledger event.

GET returns {items,latest}. items contains at most five newest completions;
latest is items[0] or null, even when its score is below an older score.
Scope is authenticated owner + quiz id + source version + grading version +
source revision. "Latest overall score" here means the newest total score for
that selected full quiz, NOT an aggregate across eras, sources or grading modes.
The UI must request the same gradingVersion; omitted GET version retains the
existing API convention of v1. Source-version changes create a separate scope.

Queue and retry invariants
Latest-five is a read projection, not deletion. Minimal immutable receipts
(hash/counts/scope/time; no raw responses) survive display eviction so an old
retry cannot mint another reward. No legacy retention/backfill/cleanup runs.
Exact retries canonicalize response ordering and UUID casing, return the
original owned receipt, and do not regrade even after a source change/outage.
Changed content or scope under a used id conflicts. Different users cannot
read another user's receipt. New attempts always load/validate the full server
source. Owner row is locked first; receipt and ledger insert share one
transaction. Same-owner completions serialize and seq DESC orders committed
history. Failed or uncertain clients must retry the SAME id and payload.

unexpected legacy mutation, source mismatch, duplicate reward, ownership leak,
unproven concurrency, or uncertain commit outcome. Do not auto-retry with a new

disable/revert the new routes, retain receipts/ledger and additive schema, and
